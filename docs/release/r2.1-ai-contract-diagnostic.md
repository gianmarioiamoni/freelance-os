## 6. REFUSAL PROTOCOL FINDING

### What each adapter requests

Neither eval adapter uses `tool_choice`, `parallel_tool_calls`, `response_format`, or a refuse tool. Both send the same application system string and the same descriptors.

**A1 (OpenAI-compatible chat completions):** native `tools[].function` with `parameters = providerArgumentSchema(...)`. Tool calls are native. If no tool calls: map `message.refusal` (OpenAI safety field) then `message.content` through `mapAdapterTextOutcome`.

**A2 (Anthropic Messages):** native `tools[]` with `input_schema = providerArgumentSchema(...)`. Tool calls are native `tool_use`. If none: concatenate text blocks and run the same normalizer. Anthropic has no native refusal field.

### What structured refusal is requested

System text: emit a refusal whose class is exactly one of `unsupported_capability`, `write_forbidden`, `injection`. Do not call a tool. Do not emit facts.

It does **not** specify `{ "refusal": "<class>" }`. Plan §21.4 states that JSON dialect is adapter-mapping input only, not the internal contract. The live model is still scored as if it had produced a controlled `AiRefusalClass`.

Accepted shapes (`normalizeRefusalCandidate`): exact class string, or JSON object with only `{ "refusal": <class> }`. Extra keys → `malformed_refusal` → `error`. Prose → `message` → orchestrator `error`.

OpenAI native `refusal` is a safety/policy channel, not this vocabulary. Mapping it through the class normalizer does not make it a first-class capability-boundary protocol. No live case produced adapter `status: "refusal"`.

### Required distinction

| # | Meaning | Evidence |
|---|---------|----------|
| 1 | Model does not recognize the unsupported request | A1 RF-02 (`list_contract_allocations`), A1 RF-04 (`list_clients`), A1 RF-06 (two tools) |
| 2 | Model recognizes it but cannot express our protocol | A1 RF-01 / RF-03 / RF-05; A2 RF-01…RF-06: no tool, prose, not a class string or envelope |
| 3 | Adapter cannot normalize a valid provider-native refusal | Not observed. Isolation tests show both adapters map a structural class onto `status: "refusal"`. No live native class-shaped refusal arrived. |
| 4 | Evaluation expects behavior not naturally represented by the provider API | Yes. Tool calling is native. Typed `AiRefusalClass` is a custom text dialect. RF-07 passes because clarification is application-side after a correct tool. RF-01…RF-06 require the model to speak the dialect. |

Capability boundaries **are** now listed in system text (hardening). That changed A1 RF-01 / RF-03 from related-list `success` to prose `error`. It did not produce first-class refusals on either provider.

This is not an adapter-normalization bug. It is a protocol-design gap: unsupported capability cannot be expressed through the same native mechanism used for tool calls.

## 9. ARCHITECTURAL FINDINGS

- The model is not financial truth. Wrong-tool `success` used the chosen tool’s DTO. Prose never became `success`. Citations were application-assembled. That architecture held on both finals.
- Orchestrator behavior is not the GP routing defect. One-tool enforcement, unknown-tool refusal, tenant-key strip, and `message` → `error` are working fail-closed paths. They convert protocol misses into `error` rather than typed `refusal`.
- E02 remains contract-scoped invoice derivation. Workspace overdue / unpaid / remaining-to-collect / unbilled indexes do not exist. RF-01…RF-04 test that product boundary. The miss is how the model must *declare* the boundary, not missing E02 financial logic.
- Tool descriptors send `name` + `description` + JSON Schema properties. Only `periodKind` / dates have enums or descriptions. Entity keys, `status`, and `tracking` are bare strings.
- First-class `AiAdapterResult.status: "refusal"` exists internally and is proven on Mock / isolation tests. Live providers never entered it.
- Contract hardening is already a demonstrated causal variable: GP-03 (A1, A2), GP-02 / GP-04 / GP-05 / GP-08 (A2). Remaining failures cannot be attributed to model incapability by default.

candidate remediation — NOT AUTHORIZED

Several remaining fails are still explained by catalog identity, discovery-vs-eval narrowing, or a refusal dialect that is not native to either provider API.
