## 1. Executive Summary

**FACT.** Diagnostic decision is `C. MIXED`. Contract hardening (`f081e914`) changed A1/A2 routing without changing models. Remaining HIGH failures are catalog identity (GP-06), question/catalog/schema mismatch plus unpublished refusal channel (GP-07), and typed-refusal protocol (RF-01 / RF-03 / RF-05). MEDIUM residuals are catalog adjacency (GP-08), related-tool leakage plus protocol (RF-02 / RF-04 / RF-06), and historical Forecast scope/null protocol (RF-08).

**FACT.** Tool calling is provider-native. `AiRefusalClass` is an application dialect. No live final produced adapter `status: "refusal"`. Prose maps to `message` → orchestrator `error`. Application safety (no write, no invented facts, no tenant leak, DTO grounding) held.

**RECOMMENDATION.** Revise the contract in eight separable layers (A–H). Do not treat remaining fails as default model incapability. Do not choose a provider to compensate for an ambiguous catalog or a non-native refusal dialect.

Target contract in one sentence:

> The model selects one allow-listed capability owner or a native refuse/clarify channel; the application alone resolves tenant, period, entity, DTO, citations, and financial truth.

## 4. Design Principles

Binding. Not optional for a later implementation.

1. **FACT / PLAN.** AI may decide what to ask and how to present. AI must not decide what is true.
2. **FACT.** Financial truth, authorization, workspace identity, and writes stay in the application.
3. **RECOMMENDATION.** Separate A–H. A miss in H must not be reported as a miss in A, and the reverse.
4. **RECOMMENDATION.** One user capability has one primary owner. Adjacent tools must state explicit non-ownership.
5. **RECOMMENDATION.** Tool *name* is not a discriminator. Ownership, input, output, MUST / MUST NOT, and competitors must be stated.
6. **FACT.** No Italian-only discriminator was introduced in hardening (plan §21.2). Any later language binding is an **OPEN DECISION**.
7. **FACT.** Prose must never become grounded `success` (§8.5 v2 C2).
8. **FACT.** First-class model refusal is not the safety hard gate (§8.5 v2 C1). Application fail-closed remains the safety gate.
9. **RECOMMENDATION.** Prefer a provider-native channel (tool calling) for any new protocol. Do not add another textual dialect.
10. **RECOMMENDATION.** Do not transform a natural Guided Prompt into a fragile exact-tool test unless the user-facing text names the capability.

## 7. Refusal Protocol Options

**FACT.** Neither eval adapter sends `tool_choice`, `parallel_tool_calls`, `response_format`, or a refuse tool. System text asks for a class string. Accepted shapes: exact class or `{ "refusal": "<class>" }` with no extra keys. OpenAI native `refusal` is a safety field, not this vocabulary. Anthropic has no native refusal field. Clarification is application-only after a tool. Unknown tool name already maps to `unsupported_capability` in the orchestrator.

Required distinction from the diagnostic still stands: recognition ≠ expression ≠ adapter mapping ≠ eval expectation.

### 7.1 Comparison

| | A. Typed textual refusal | B. Native structured output / provider refusal | C. App classification after structured model output | D. Control / sentinel tool | E. Other: two-step classify-then-act |
| --- | --- | --- | --- | --- | --- |
| Mechanism | Class string or JSON in `message` | Provider JSON mode / native safety refusal | Model emits a controlled envelope; app maps class | `refuse` (name TBD) with enum `class` via native tools | Extra round-trip |
| Provider compatibility | Universal text; **FACT:** 0 live first-class hits | Divergent: OpenAI safety ≠ our classes; Anthropic no refusal field; JSON mode not universal | Needs *some* structured channel | Uses the channel both eval providers already use | Extra latency/complexity |
| A1 compatibility | Failed live | Would be A1-specific if it used OpenAI JSON/refusal | Possible if A1 emits the envelope | Compatible in principle (native functions) | Compatible, not measured |
| A2 compatibility | Failed live | Weak (no native refusal; JSON tool-less output is not the current adapter) | Same envelope if A2 emits it | Compatible in principle (native `tool_use`) | Same |
| Self-host / OSS | Works if the model follows the dialect | Often absent or different | Depends on structured output support | Works if the runtime has tool calling; else fall back to `parseProviderEnvelope` | Worse on small models |
| Security | Fail-closed today: prose → `error`, extra JSON keys → `error`, no facts on refusal | Native safety refusal must not be trusted as capability-boundary | Classifier must be allow-listed classes only; no prose facts | Tool `readOnly`; execute returns no DTO; orchestrator must not assemble `success`; strip tenant keys | Second call must not see tenant dumps |
| Implementation complexity | Already built | Per-provider branches - conflicts with provider-agnostic hardening | New envelope + classifier | New allow-listed tool + orchestrator branch | Highest |
| Failure modes | Recognize-but-prose (RF-01/03/05); related-tool leak (RF-02/04); multi-tool (A1 RF-06) | Mapped safety ≠ `write_forbidden` / `unsupported_capability` | Model emits unstructured text anyway | Model still calls a related read instead of refuse; refuse-as-success if orchestrator is wrong | Classifier error becomes systematic |
| Evaluation | Current cases require `outcome=refusal` + class | Would still need adapter mapping into `AiRefusalClass` | Layer 6 = envelope shape; Layer 5 = no execute | Layer 6 = refuse tool + class; Layer 5 = no related read | Two layers of protocol |

### 7.2 Recommendation

**RECOMMENDATION.** **D as the primary expression channel. Keep A as fail-closed fallback. Do not adopt B as the internal contract.**

- D puts unsupported/write/injection on the same native mechanism as reads. That is the diagnostic’s architectural gap.
- A remains: any class-shaped text still normalizes to `refusal`; any other prose stays `error`, never `success`.
- B may be used *inside* an adapter as a mapping source only (already true for OpenAI `message.refusal`). It must not become the application protocol.
- C is complementary for envelope parsing (`parseProviderEnvelope` already exists for non-native runtimes). It is not sufficient alone for native-tool providers that never emit that envelope.
- E is not recommended for R2.1: second model hop, cost, and a new truth-decider.

**RECOMMENDATION.** Sentinel tool constraints if later authorized:

- `readOnly: true`
- args: `class` enum of model-emitted classes only: `unsupported_capability` | `write_forbidden` | `injection`
- `execute` does not call services, Prisma, or SQL
- orchestrator maps it to `outcome: "refusal"` and empty facts/citations
- unknown class → `error` (fail closed)
- must remain on the allow-list; unknown names already refuse

D does **not** fix related-tool leakage by itself. Leakage is catalog exclusivity + model recognition (RF-02 / RF-04). Those stay Layer 2 / Layer 5.

**CLOSED.** R21-OD-CR-04 = gate **B** (native sentinel `refuse`; prose → `error`). **DEFERRED.** R21-OD-CR-05 (§8.5 roles unchanged). See `docs/release/r2.1-ai-contract-revision-decisions.md`.
