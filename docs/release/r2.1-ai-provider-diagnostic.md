## 4. Evidence

### GP-03 / GP-04 — can the model distinguish the four revenue tools?

Exposed descriptions:

| Tool | Description | Args |
| --- | --- | --- |
| `get_accrued_revenue` | Authoritative Accrued Revenue for a supported period. | period + entity keys |
| `get_expected_revenue` | Authoritative Expected Revenue for a supported period. Nulls are preserved. | period + entity keys |
| `get_current_month_analytics` | Current-month hours, Accrued, Expected, Forecast, client allocations, and contract utilizations. | none |
| `get_monthly_analytics` | Hours, Accrued, Expected, and Forecast for a supported reporting period. | period keys |

Distinction is **not** sufficiently explicit. Accrued / Expected appear on the overview tools. Nothing says “do not use overview for a single revenue metric.” Names of the specialized tools match the questions more closely than the overview name; the model still chose the zero-arg current-month tool. That is recorded behavior, not inferred motive.

### GP-05 — why `periodKind=current` → `invalid_period`

| Layer | Fact |
| --- | --- |
| Provider schema | `periodKind: { type: "string" }`. No enum. |
| Tool description | Uses the word “current” (“certified current period”). |
| Adapter | Parses JSON arguments. Does not map or default `periodKind`. |
| Application | `PERIOD_KINDS = today \| week \| month \| year \| custom`. Unknown → `invalid_period`. Missing `periodKind` → `month`. |
| Verdict | `current` is valid in the provider-facing schema and invalid internally. The model emitted a non-enum string. The adapter did not transform it. Application validation rejected an otherwise intended Forecast call. |

### GP-08 — why `list_contracts` not `get_contract_report`

From the model-visible text the two tools overlap on “contracts.” They do **not** overlap on payload: commercial fields vs utilization/allocation/revenue. “Richiedono attenzione” is not bound to either description. Recorded selection: `list_contracts`. Semantic overlap from the model’s perspective: **yes, on the name; no, on the description.**

### RF-01 / RF-03 — why `list_clients` not refusal

Unsupported collection / workspace-invoice capability is not stated in the system string. The only explicit “workspace invoice index is unsupported” line sits on `list_invoices_for_contract`, which requires `contractId`. `list_clients.status` is an unconstrained string, so `active` / `unpaid` look schema-legal. Recorded: substitute read, then application `success`.

### RF-02 / RF-04 / RF-05 / RF-06 — why `error` not `refusal`

| Check | Recorded |
| --- | --- |
| Tool attempted | No |
| Malformed JSON | No (harness count 0) |
| Unsupported / write tool name | No |
| Application path | `status: message` → `parseProviderEnvelope` → `kind: message` → orchestrator `error` |

Mock refusals are scripted as `{"refusal":"unsupported_capability"}` (or `write_forbidden` / `injection`). That format is application-supported and **not** described to the live model. Prose is correctly treated as non-truth (`error`), not as a typed refusal.

## 5. Mock vs live distinction

Mock GP/RF cases pass because `scriptForAnalyticsEvalCase` emits the **already-correct** tool call or JSON refusal. That proves:

- orchestrator, sanitization, period/entity validation, grounding, and citation assembly for those scripted decisions;
- application-boundary SEC-* behavior when the model misbehaves.

It does **not** prove:

- live tool routing;
- live period-arg legality;
- live structured refusal.

Mock success is not evidence that A1 should pass §8.5.

## 6. Likely root causes

1. **Overview tools advertise Accrued / Expected / Forecast** → GP-03, GP-04, RF-07 collapse to `get_current_month_analytics`.
2. **Period keys are untyped strings** → GP-05 `current`; RF-08 `month` + dates. Application enum/pairing is invisible to the model.
3. **Contract tool names collide** → GP-08 `list_*` vs `get_contract_report`.
4. **Refusal is an undocumented JSON side-channel** on the native tool-calling path → RF-02/04/05/06 become `error`.
5. **Unsupported capabilities are not listed in system instructions** → RF-01/03 nearest-list substitution.
6. **`list_clients.status` is not an enum** → `active` / `unpaid` accepted then ignored (contributes to `success`).
