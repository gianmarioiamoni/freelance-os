### 2.3 Authoritative calculation owners

| Calculation / rule | Current owner | Persisted? |
| --- | --- | --- |
| Accrued Revenue | `AnalyticsService.getAccruedRevenue` / `calculateAccruedRevenue` | No. Derived from TimeEntry commercial snapshots |
| Expected Revenue | `AnalyticsService.getExpectedRevenue` / `calculateExpectedRevenue` | No. Live Contract commercial config + pro-rata. DAILY ⇒ null. HOURLY without capacity ⇒ null |
| Forecast Revenue | `AnalyticsService.getForecastRevenue` / `calculateForecastRevenue` | No. Accrued / elapsedFraction. Current certified period only. Else null |
| Hours / billable % / client allocation / contract utilization | `AnalyticsService` | No |
| Contract allocation status | `AnalyticsService.calculateContractAllocation` / `deriveAllocationStatus` | No. Null/0 allocation ⇒ no status |
| `paidAmount` | `sumPaidAmount` over Payment rows | No |
| `amountStatus` UNPAID / PARTIAL / PAID / MISMATCH | `deriveAmountStatus` | No |
| `overdue` | `isOverdue` (dueDate + workspace today + unpaid remainder) | No. Null dueDate ⇒ never automatic overdue |
| Invoice tracking state ACTIVE / VOID | `invoiceTrackingState(voidedAt)` | `voidedAt` persisted; state derived |
| Payment/invoice currency invariant | Create/update services copy Contract/Invoice currency. Client currency cannot diverge | Snapshot persisted; mutation forbidden |
| Contract validity `[validFrom, validTo)` | Contract application + domain overlap | Persisted interval |
| TimeEntry validation | `validateTimeEntryInput`, contract eligibility at create | Duration 1–1440; `workDate` / `clientId` / `contractId` immutable after create |
| Invoice validation | `parseInvoiceCreateInput` / update parser + domain due-date consistency | Amount > 0; VOID is one-way |
| Payment validation | `parsePaymentCreateInput` + active-invoice guard | Amount > 0; VOID invoice not editable |
| Alert semantics | `AlertService` + allocation/payment evaluators over Analytics / derived invoice fields | Alert/Notification rows persisted; condition is re-derived |
| Workspace authorization | Session → `resolveWorkspaceContext` / `requireWorkspaceAccess` | Membership persisted |
| Period / “today” | `Workspace.timezone` | Workspace timezone persisted |

**R2 DECISION.** Accrued, Expected, Forecast, Invoice, and Payment are independent (D4). AI must not collapse them into one “revenue” number.

**R2 DECISION.** Forecast is linear and not ML (R2-OD-005). AI must not invent a smarter forecast.

**R2 DECISION.** No FX and no mixed-currency total. Publication is per currency.

## 4. Deterministic vs AI responsibility model

**PROPOSAL.** This is the R2.1 responsibility boundary.

### A. Deterministic only

AI must never perform the authoritative operation.

Examples: Accrued / Expected / Forecast arithmetic; `paidAmount`; `amountStatus`; overdue; allocation status; contract overlap/validity; TimeEntry / Invoice / Payment validation; currency snapshots; VOID; alert create/resolve; workspace membership; CSV numbers; publication rounding.

### B. AI read / interpret

AI may parse natural language into a structured request and call a controlled read.

Examples: “ore questo mese” → `getCurrentMonthAnalytics`; “Accrued ACME agosto” → resolve client + month period → `getAccruedRevenue`; “utilizzo contratto X” → `getContractUtilizations` / `getContractAllocation`.

### C. AI summarize / explain

AI may turn deterministic DTOs into prose. Every money figure in the prose must come from the DTO.

Examples: explain why Forecast is null on a historical period; explain Accrued ≠ Expected ≠ invoiced ≠ paid; summarize current-month hours and Accrued by currency.

### D. AI suggest

AI may point at patterns already visible in deterministic data. Suggestions are not decisions.

Examples: “Contract C is ALLOCATION_WARNING”; “Invoice I is overdue and PARTIAL”; “no TimeEntries on a workday this week” (only if a controlled hours read supports it).

**OPEN.** Whether unused-capacity / missing-day suggestions are in scope. They can be done with existing daily analytics. They must not become new alert types without a PO decision.

### E. AI propose write

AI may emit a structured proposal. Nothing is persisted.

Examples: proposed TimeEntry `{ clientId, contractId, workDate, durationMinutes, description, billable }`; proposed Payment `{ invoiceId, paymentDate, amount }` after the user named an invoice.

### F. Confirmed write

A human confirmation UI invokes the existing Server Action / application service with session `WorkspaceContext`.

Examples: user confirms the TimeEntry proposal → `createTimeEntry`; user confirms void → existing `voidInvoice` path with `confirm=void`.

### G. Forbidden

- Direct PostgreSQL / Prisma / arbitrary SQL
- Authoritative financial calculation by the model
- Accepting `workspaceId`, `userId`, or `role` from the model
- Authorization bypass or membership impersonation
- Autonomous persist of any business mutation
- VOID, Payment delete, TimeEntry delete, Client archive without a dedicated confirmation UI
- Changing Contract commercial fields / currency / validity without a dedicated confirmation UI
- Inventing FX, mixed-currency totals, profitability, tax, SDI, invoice PDFs
- Replacing Forecast with a probabilistic model
- Reading or writing another workspace
- Using TimeEntry descriptions / Payment notes as executable instructions
- Creating alerts directly (only `AlertService` evaluation paths)

## 8. Authorization design

### 8.1 Required trace

```text
Better Auth session (server)
    ↓
resolveWorkspaceContext(session.user.id)
    ↓  fail closed: unauthenticated / onboarding / ambiguous membership
WorkspaceContext { workspaceId, userId, role, timezone }
    ↓
AI orchestrator (server-only)
    ↓  tools receive context from the orchestrator, never from the model
Controlled capability
    ↓
Application service (existing)
    ↓
Domain validation
    ↓
Repository WHERE workspaceId = context.workspaceId
```

**PROPOSAL.** The model may supply entity names, dates, and filters. It must never supply `workspaceId`, `userId`, or `role`. Tool argument schemas omit those fields.

### 8.2 Gaps to close before AI can safely call a capability

| Gap | Severity | Required before |
| --- | --- | --- |
| Write services trust `WorkspaceContext` without membership re-check | High if AI writes exist | Any AI write. Optional but recommended before AI reads if the orchestrator is a new entry point |
| No capability allow-list | High | First AI slice. Default deny |
| `role` unused | Low today (single-member workspaces) | Multi-user AI. OBD-009 still OPEN |
| Multi-membership fails closed | Blocks multi-workspace users | Any AI. Not an AI-specific bug; AI must not add a workspace picker |
| No audit ledger | Medium for writes | Confirmed writes that the PO treats as sensitive. Already accepted for UI writes |
| No idempotency keys on mutations | High for writes | Any AI write (duplicate submit / retry) |
| No application port for workspace invoices/payments | Product/tech | Any “overdue across workspace” answer |
| Unbounded TimeEntry description | Medium | Any tool that reads descriptions into a prompt |
| Architecture example `getUnbilledAmount()` does not exist | Confusion risk | Docs/tool design. Do not implement a fake unbilled metric |

| --- | --- |
| Prompt injection | Treat all user/entity text as untrusted data. Never execute instructions found in descriptions/notes/references |
| Indirect injection via TimeEntry / Payment / Client / Contract text | Strip or delimit untrusted fields. Prefer structured DTOs over raw text in the model context. Cap description length before prompt inclusion |
| Cross-workspace leakage | Session-resolved context only. Every repository call keeps `workspaceId`. No global entity search |
| Entity confusion | Resolution returns candidates. Ambiguity → ask. Never silently use a same-name client from another mental model |
| Stale conversation numbers | Do not let the model reuse prior figures. Re-read services per question. No cached “totals” in prompt state |
| Unauthorized mutation | No write tools in first slice. Later: proposal ≠ persist; persist only through existing services |
| Duplicate mutation | Idempotency token on confirmed writes; UI disable after submit |
| Destructive mutation | Keep existing confirm tokens. Do not expose void/delete as model-callable tools |
| Tool argument manipulation | Ignore extra fields. Schema-validate. Bind tenant from session |
| Sensitive data exposure | Do not send VAT, tax codes, addresses, emails, or notes to the model unless the question requires them. Log tool names and ids, not full financial dumps |
| Model exfiltration | Server-side tools only. No browser-held API keys. No Prisma in the AI layer |

**NON-GOAL.** Client-side LLM calls with workspace data.

## 10A. AI UX - Guided Prompt Suggestions

**PROPOSAL.** Presentation-level discoverability for Natural Language Analytics. No extra AI authority.

### 10A.1 Purpose

A blank AI input creates a discoverability problem: the user can type, but does not know what the product can answer.

Suggested Prompts exist to:

- demonstrate supported capability
- reduce the blank-chat problem
- teach the kinds of questions that are supported
- reduce onboarding friction
- give examples of natural-language interaction

They must not:

- define a restricted command language
- replace free-form questions
- expose internal tool names
- imply capabilities that do not exist

Every displayed prompt must map to an explicitly supported first-slice read. Do not advertise workspace-wide Invoice/Payment questions (`Quali fatture sono scadute?`) while that application port is missing.

### 10A.2 First-slice UX

Preferred first-slice surface:

- constrained ask-box on Dashboard and/or Reports
- a small set of suggested prompts next to the input
- free-form question remains available
- click a suggestion → populate or submit that natural-language question (**OPEN** which)
- read-only. Same orchestrator path as a typed question

Visual design is not finalized here. No chip library, placement, or copy system is authorized by this section.

### 10A.3 First-slice prompt catalog

Examples of supported natural language, not proprietary commands. Distinct capabilities only. All rows: AI role = interpret intent, select a controlled read, explain/summarize the DTO. Side effect = **NO**.

#### Overview

| Prompt | Capability | Data source | AI role | Side effect |
| --- | --- | --- | --- | --- |
| Come sto andando questo mese? | Current-period briefing | `AnalyticsService.getCurrentMonthAnalytics` | Interpret + read + explain | NO |
| Cosa dovrei sapere di questo mese? | Same briefing, attention-oriented phrasing of current-month DTO (hours, Accrued, Expected, Forecast, utilization/allocation already on the DTO) | `getCurrentMonthAnalytics` | Interpret + read + explain | NO |

Do not treat the second row as a new insight engine or a second alert channel.

#### Revenue

| Prompt | Capability | Data source | AI role | Side effect |
| --- | --- | --- | --- | --- |
| Quanto ho maturato questo mese? | Accrued Revenue, current month | `getAccruedRevenue` or Accrued on `getCurrentMonthAnalytics` / `getMonthlyAnalytics` | Interpret + read + explain | NO |
| Qual è il mio Expected Revenue? | Expected Revenue, current month | `getExpectedRevenue` or Expected on monthly analytics. Explain null for DAILY / no capacity | Interpret + read + explain | NO |
| Qual è il mio Forecast? | Forecast Revenue, current certified period | `getForecastRevenue` or Forecast on monthly analytics. Explain null if not current period | Interpret + read + explain | NO |

Accrued / Expected / Forecast are already user-facing R2 terms. The answer must keep them independent (D4).

#### Time

| Prompt | Capability | Data source | AI role | Side effect |
| --- | --- | --- | --- | --- |
| Quante ore ho lavorato questo mese? | Hours for current month | Monthly analytics hours fields | Interpret + read + explain | NO |
| Come sono distribuite le mie ore? | Hours by client / allocation | `ReportingService.getHoursByClient` or `getClientAllocations` for the current month | Interpret + read + explain | NO |

#### Contracts / Allocation

| Prompt | Capability | Data source | AI role | Side effect |
| --- | --- | --- | --- | --- |
| Quali contratti richiedono attenzione? | Utilization / allocation status already computed | `getContractUtilizations` and/or `listContractAllocations` for the current period | Interpret + read + explain | NO |
| Quali contratti stanno consumando più rapidamente l'allocazione? | Allocation consumption vs budget | `listContractAllocations` / `getContractAllocation`. Skip or say “no allocation” when allocatedMinutes is null or 0 | Interpret + read + explain | NO |

#### Explicitly excluded from the first-slice catalog

| Do not display | Why |
| --- | --- |
| Quali fatture sono scadute? | No workspace Invoice index |
| Cosa ho incassato questo mese? | No workspace Payment index |
| Cosa posso fatturare? / unbilled | Metric does not exist. Accrued ≠ unbilled |
| Registra 3 ore su ACME | Write. Out of first slice |
| Period-over-period “principale cambiamento” as a first-slice chip | No comparison application port. Do not advertise |

Invoice/Payment questions remain possible later only when scoped to a known contract/invoice id, or after a deterministic workspace index exists. They are not first-slice suggestions.

### 10A.4 Contextual prompts - deferred

Suggested Prompts may later become page-aware. Not implemented. Not required for the first slice.

| Surface | Possible later prompts | First slice? |
| --- | --- | --- |
| Dashboard | Come sto andando questo mese?; Cosa richiede la mia attenzione? | Default catalog may live here. Page-specific variants are optional |
| Reports | Spiegami questo report. | Deferred. Would explain the already-loaded report DTO, not a new calc |
| Reports | Qual è il principale cambiamento rispetto al periodo? | Deferred / do not advertise until a comparison read is defined |
| Contract detail | Come sta andando questo contratto?; Quanto dell'allocazione abbiamo consumato? | Deferred. Would bind `contractId` from the route, not from the model |

**PROPOSAL.** First release: one small generic catalog on the Dashboard/Reports ask-box. Contextual catalogs later. Mixing both in v1 is an OPEN product choice, not a default.

### 10A.5 Prompt quality rules

- Natural language, short, outcome-oriented
- Understandable without engineering knowledge
- Use R2 user-facing terms only (Accrued / Expected / Forecast / allocation are allowed)
- No internal tool names, no command syntax
- No fake capabilities, no implied write
- No LLM-authoritative calculation; numbers come from the same services as the catalog
- Distinct capabilities, not many phrasings of the same read
- If a capability is removed or not yet shipped, remove the prompt in the same change

### 10A.6 Prompts as evaluation cases

The catalog is also the first golden-question set. Do not implement an eval framework yet.

Example: `Come sto andando questo mese?` should later assert:

- intent recognized as current-period briefing
- correct read selected
- period = workspace current month
- workspace scoped from session
- answer figures match the DTO
- no invented totals, FX, unbilled, or overdue-workspace claims

UX discoverability and regression evals can share one catalog.

### 10A.7 Architectural impact

Suggested Prompts do **not** expand AI authority. They are presentation-level strings that enter the same path as a typed question:

```text
UI (ask-box + suggested prompts)
 ↓
AI Orchestrator
 ↓
Allow-listed read capabilities
 ↓
Existing Application Services
 ↓
Domain
 ↓
Repositories
 ↓
PostgreSQL
```

No special execution path. No catalog-to-service shortcut that bypasses the orchestrator. Clicking a prompt is equivalent to submitting that sentence.

## 12. Cost / complexity / minimum viable AI infrastructure

| Concern | Minimum for E01+E02 | Not required for first slice |
| --- | --- | --- |
| Model/API dependency | One provider, server-side, secret in env | Multi-provider routing |
| Latency | Target < 5s for a single-tool read + short answer. Show pending state | Streaming chat theatre |
| Token cost | Send DTOs, not raw table dumps. Cap rows. No conversation history beyond the current question + last tool result | Long memory |
| Observability | Request id, user id, workspace id, tool names, latency, token counts, error class. No full PII in logs | Full prompt archive |
| Retries | Retry provider 5xx only. Never retry a write | Autonomous repair loops |
| Structured outputs | JSON intent or tool calls with Zod-validated args | Free-form tool graphs |
| Tool calling | Allow-listed read tools only | Write tools |
| Conversation state | Stateless per question, or one-turn | Multi-day threads |
| Privacy | Workspace data leaves the app to the provider. Disclose this. OPEN: provider region / no-training contract | On-prem model |
| Testing / evals | Unit: orchestrator never forwards workspaceId; tools bind session. Golden questions with fixture DTOs, starting from the §10A catalog. Mock the provider (`docs/testing-strategy.md` §31) | Live production eval harness |
| Production monitoring | Tool error rate, empty-resolution rate, latency, cost per workspace | Quality A/B |

**PROPOSAL. Minimum viable AI infrastructure**

    ↓

    ↓

## 13. Architectural proposal

The repository supports the planned adapter shape. No alternative is indicated.

```text
UI
 ↓
AI Orchestrator          ← owns intent, tool selection, prose, citations
 ↓
Controlled read tools    ← own argument validation; bind session context
 ↓
Existing application services
 ↓
Domain                   ← owns invariants and derivation
 ↓
Repositories
 ↓
PostgreSQL
```

| Layer | Owns | Does not own |
| --- | --- | --- |
| UI | Ask-box, citation rendering, later confirmation panels | Authorization, numbers |
| AI Orchestrator | NL interpretation, tool choice, explanation | Tenant choice, arithmetic, persistence |
| Tools | Mapping args → service calls | SQL, context construction from the model |
| Application services | Use cases, membership where already implemented, orchestration | Prompting |
| Domain | Validation, derived invoice/allocation/forecast rules | HTTP, LLM |
| Authorization | Session + membership **before** the orchestrator | Model claims |
| Validation | Existing parsers/services on every write | Model-supplied “it looks valid” |
| Human confirmation | Presentation, after a proposal, before the existing write path | The model |
| Authoritative calculations | AnalyticsService + invoice/payment domain helpers | The model |

**PROPOSAL.** Put the orchestrator in Application or a sibling `application/ai` adapter that depends inward on existing services. Do not put it in Domain. Do not give it Prisma.

This matches A-009 and `MASTER_PLAN.md` §21. It does not require R3 integration adapters.

## 17. Discovery conclusion

### A. Does AI provide enough real product value to justify R2.1?

**Yes, narrowly.** R2 already has the deterministic operational core AI was waiting for. The valuable job is not “AI in the product.” It is: map a freelancer’s language onto the correct existing metric and explain Accrued vs Expected vs Forecast vs invoiced vs paid, without leaving Reports.

Guided Prompt Suggestions strengthen the UX case for that first read-only slice by making supported questions immediately discoverable. They add no AI authority and no data risk when they are only presentation-level examples of existing reads. They do not, by themselves, prove that AI is valuable.

AI is **not** justified as a second calculation engine, a chat replacement for forms, a proactive insight feed, or an autonomous back-office.

A non-AI workspace Invoice index and alert-link UX may outperform AI for collection and alerts. Those should not be delayed solely to “do AI.”

### B. First implementation candidate

If the PO approves R2.1:

1. **R2.1-E01 AI Foundation** - server orchestrator, session-bound context, allow-listed read tools, provider mock, eval fixtures.
2. **R2.1-E02 Natural Language Analytics** - contextual ask on Dashboard/Reports, including the default briefing “come sto andando questo mese?” and Guided Prompt Suggestions as part of that UX (not a separate Epic).

No writes. No global chat product. No new financial formulas.

### C. Explicitly out of scope

- Autonomous writes
- VOID / delete / contract commercial edits via AI
- ML Forecast / FX / unbilled invention
- Workspace-wide invoice scan implemented only inside the LLM
- R3 integrations
- Proactive insight engine
- Direct DB access

### D. Can R4 reasonably be advanced ahead of R3?

**Technically yes.** R3 is external integrations. The AI adapter depends on R2 application services, not on SDI, calendar, or accounting. Advancing a **thin R2.1** does not require R3.

**Process: OPEN.** `MASTER_PLAN.md` §8 says releases are sequential and the current header forbids starting R3. R2.1 is not on that roadmap. The PO must authorize the exception. This document does not update MASTER_PLAN.

### E. Architectural prerequisites before implementation

- Keep R2 services as the only source of numbers
- Session → WorkspaceContext → tools (no tenant args from the model)
- Capability allow-list, default deny
- Membership re-check on any new AI entry point (mandatory before writes; recommended on Foundation)
- Untrusted-text handling for descriptions/notes
- Provider secret, timeout, structured outputs, mocked tests
- Citation object so the UI prints service numbers
- Decision on workspace invoice port if collection questions are in scope

### F. PO decisions required

See §15. The blocking ones are: authorize R2.1; MASTER_PLAN status; provider/privacy; first UX; whether collection questions wait on a deterministic invoice index. Suggested-prompt click/populate and generic-vs-contextual are UX decisions, not blockers for authorizing R2.1.

### G. What should not be implemented yet

- Any code, dependency, route, schema, UI, agent, or tool
- Timesheet / invoice / payment write tools
- Conversation memory
- Background insight jobs
- Changes to R2 calculation semantics
